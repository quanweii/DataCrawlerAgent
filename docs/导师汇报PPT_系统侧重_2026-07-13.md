# Slide 2 — 问题：新域 MAG benchmark 又贵、又漏、又不可复用 ⏱1'

**三句话问题**（每句对应系统的一个反命题）：
1. **贵**：专家手建一个新域 MAG 动辄几个月（爬数据 / 定义节点边 / 清洗 / 对齐模态 / 切分）。
2. **漏**：多数 benchmark 不剪跨切分边，测试标签顺着图连通性就泄露出（标签传播不用特征能到 0.9+）→ 结论不可信。
3. **不可复用**：每换一个域，爬虫 / 清洗 / 建图逻辑要重写一遍，没有声明式、可扩展的标准。

**我们的位置**：OpenMAG 把"多模态图评测"做得很全，但**没解决"防泄露"和"流水线可复用"**这两件最根本的事。

🎤 **口播**：为什么做这个，三句话。建新域 benchmark 很贵；多数 benchmark 带隐性泄露、结论不可信；建图的流水线代码每换一个域就重写。OpenMAG 广度做满了，但恰恰没碰这两件根本问题。所以我们的贡献在"可复用的防泄露建图系统"，不在评测广度。

# Slide 3 — 系统总览：分层架构（头条页）⏱2'

**四层架构**（自顶向下）：

| 层 | 组件 | 作用 |
|---|---|---|
| **L1 声明层** | `domains/*/domain.yaml` + `build-mag-dataset` skill | 用户只写 YAML；skill 引导零代码建域 |
| **L2 编排层** | `OrchestratorAgent`（LLM 动态调度） | 规划 / 选下一个 agent / 重试决策 / 接反馈回路 |

| **L4 引擎层** | `build_graph_from_config` 通用建图 + `benchmark/` 评测 + LP-ceiling 测量 | 真正干活的确定性代码 |

**贯穿层**：`Blackboard`（共享状态，namespace 隔离）+ `MessageBus`（agent 间消息：quality_issue / reprocess_request）。

**一句话**：上层声明、中层智能、底层确定；agent 负责"编排 + 语义 wrangling + 对抗闭环"，确定性测量与建图交给引擎层。

# Slide 4 — Agent 抽象：三层继承 + 一个认知循环 ⏱1.5'

**继承链**：
- **`BaseAgent`**（`base_agent.py`）：LLM 调用模板 + 瞬时错误重试（指数退避）+ `reason_about_task()` / `evaluate_own_results()`。抽象 `execute()`。
- **`ReActAgent`**（`react_agent.py`，继承 BaseAgent）：**Observe → Think → Act** 循环 + 状态机（IDLE/OBSERVING/THINKING/ACTING/COMPLETED/FAILED）。子类只需实现 `get_available_actions()` / `is_done()` / `observe()` / `act()`，`think()` 由基类用 LLM 选 action。
- **专才 Agent**（collector / graph_builder / formatter / verifier）：各自声明自己的 action 清单，复用同一个认知循环。

**可复用细节①**：**一个认知循环，喂给所有专才**。加一个新 agent = 写一个 action 清单 + 几个 action 方法，零编排代码。

**可复用细节②**：ReAct 的 `think()` 输出严格 JSON（`{action, params, reasoning}`），无效 action 自动回退 `_default_action()`——**LLM 不稳也不会让流水线崩**。

# Slide 5 — 多智能体通信：Blackboard + MessageBus ⏱1.5'

**两套正交通信原语**（`messages.py`）：

| 原语 | 语义 | 代码事实 |
|---|---|---|
| **Blackboard** | 共享状态，按 namespace 隔离，线程安全 | `write/read/read_namespace/snapshot`；namespace：`global` + 每域 `collector/graph/formatter/verifier` |
| **MessageBus** | 点对点 + 广播消息，per-agent 队列 | `Message(sender, recipient, msg_type, content, priority)`；类型：`quality_issue` / `reprocess_request` / `status` / `result` |

**可复用细节③**：**状态走 Blackboard，控制流走 MessageBus**——agent 之间不直接调用，彻底解耦。Verifier 发一条 `reprocess_request(priority=2)` 就能让 Builder 重跑，Builder 不需要知道 Verifier 存在。

**可复用细节④**：namespace map 让同一套通信基础设施**同时服务 arxiv/reddit/amazon/steam/tmdb/wikiart 六个域 + 任意 YAML 动态域**，零修改。

# Slide 6 — Orchestrator：LLM 动态调度循环 ⏱1.5'

**`OrchestratorAgent.run_pipeline()` 主循环**（`orchestrator_agent.py`）：
1. **`analyze_task()`**：LLM 读 `DomainConfig.agents_desc`，生成 `PlanStep[]` 动态计划（失败回退默认 plan factory）。
2. **`decide_next_agent()`**：依赖满足的 pending 步骤里选一个；多个可运行时 LLM 裁决。
3. **执行**：注入 blackboard/message_bus，跑 agent 的 ReAct 循环。
4. **评估**：`success/partial` → completed；失败 → `should_retry()`（LLM 判断值不值得重试）。
5. **反馈回路**：每次完成后扫描 MessageBus 的 `reprocess_request`（见 Slide 7）。

**可复用细节⑤**：**`_default_plan_co_attribute()` 从 `agents_desc` 动态发现 agent 名**——collector → graph_builder → formatter → verifier 这条链不是硬编码，新域注册即自动生效。

**可复用细节⑥**：`critical_agents` 集合决定"失败即终止"还是"容忍继续"——**容错策略也是声明式的**。

# Slide 7 — 对抗闭环（承重关节）：Verifier → Builder reprocess ⏱2'

> 这一页是"多智能体"真正承重的关节，也是与"单脚本流水线"拉开差距的地方。

**`GraphVerifierAgent`（ReAct agent，排在 formatter 之后）的 action 清单**：
- `load_graph` → 从 blackboard 读图
- `check_leakage` → **LP-ceiling 双报**（原始 vs 剪枝 vs 多数类基线）；超额 > 0.10 = 结构泄露
- `check_homophily` → **逐关系同质性**；某关系 homo > 0.95 且 ≥50 边 = 定义性泄露（边类型 ≡ 标签）
- `check_coverage` → 孤立节点过多 = collector/builder 不完整
- `report_issues` → 汇总，发 `reprocess_request(priority=2)` 给 Builder

**Orchestrator 的回路实现**：接到 reprocess → 生成 reprocess PlanStep → **级联**把 Builder 所有下游 completed→pending → 重建。`MAX_REPROCESS_ROUNDS=2` 防死循环。

**承重 vs 不承重（诚实红线）**：
- ✅ **承重**：这条对抗闭环的 *plumbing*（一个 agent 的缺陷被另一个 agent 发现并纠正、级联重建）——手工脚本做不出。
- ⚠️ **不承重**：泄露的 *判定*（LP-ceiling > 多数类）是 `benchmark/` 里确定性测量，**不靠 LLM**（与 greedy=oracle 一致）。

# Slide 8 — 声明式域层：1 YAML = 1 域（两座桥）⏱1.5'

**`DomainYamlConfig` schema**（`domains/domain_schema.py`）——一个 YAML 完整描述一个 co-attribute MAG 域：
```yaml
domain: spotify
data:
  id_field: track_id
  label_field: playlist_genre
  min_class_size: 20
  data_source: file
relations:
  - { name: same_artist, group_by: track_artist, cap: 30, freq_filter: 0.30 }
  - { name: same_album,  group_by: track_album_id, cap: 10 }
output_dirs: { raw, items, graphs, datasets }
```

**两座桥**（YAML 不碰任何框架代码）：
- `yaml_to_domain_config()` → 动态生成 `DomainConfig`，`register_domain_config()` 注册 → **编排器零修改**
- `yaml_to_graph_config()` → 生成 `build_graph_from_config` 的 config dict → **建图引擎零修改**

**可复用细节⑦**：`load_domain_yaml()` 内置**校验**（必填字段、cap>0、freq_filter∈(0,1]）；`{domain}` 路径占位符自动插值。YAML 写错在加载时就挂，不会跑半截。

**对照（来自 `domains/README.md`）**：

| | 旧（硬编码） | 新（YAML） |
|---|---|---|
| 新建文件 | 4+ 个 Python | **1 个 YAML** |
| 修改既有文件 | 11+ 处 | **0 处** |
| 域注册触点 | 11 处 | **自动** |

# Slide 9 — 通用建图引擎：build_graph_from_config ⏱1.5'

**可复用细节⑧：三种 filter 时序，一套代码**
- `filter-then-build`（steam 模式）：先过滤小类，再用保留节点建边

- `genres[0]` → 列表首元素当 label

# Slide 14 — Takeaways + 诚实定位 + Q&A ⏱0.5'

**系统贡献（三句话）**：
1. **可复用的认知内核**：BaseAgent→ReActAgent→专才，一个 Observe-Think-Act 循环喂所有 agent；Blackboard/MessageBus 解耦通信。
2. **可复用的扩展面**：1 YAML = 1 域（两座桥，框架零修改）+ 通用建图引擎 + 7 阶段 skill → spotify 零代码、三域 94.6% 复用。
3. **可复用的质量门**：Verifier→Builder 对抗闭环（plumbing 承重；判定靠 LP-ceiling 测量，与 greedy=oracle 一致）。

**诚实定位（agent 的承重边界）**：
- agent **承重**：citation 语义 wrangling（arxiv 独有）+ 可复用接口 + 编排与对抗闭环 plumbing。
- agent **不承重**：去泄露决策（greedy=oracle 已证测量驱动）。
- → 这条红线让消融打不穿自己，是本工作最大的防御资产。

**剩余工作**：论文初稿（逻辑线 + 实验已齐）+ 发布打包（Zenodo/HF DOI、leaderboard、贡献者指南）。

🎤 **口播**：总结三句话。第一，一套可复用的认知内核——所有 agent 共享一个 ReAct 循环，通信彻底解耦。第二，一套可复用的扩展面——1 个 YAML 等于 1 个域，框架零修改，spotify 零代码、三域 94.6% 复用。第三，一道可复用的质量门——Verifier→Builder 对抗闭环。最后强调诚实定位：agent 承重的是语义 wrangling、可复用接口和编排 plumbing，不承重去泄露决策，这条红线让消融打不穿自己。谢谢老师，请提问。
